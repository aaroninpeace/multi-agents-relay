# 核心原则 P1–P5

> 这些是协议的地基。与具体工具、模型、仓库结构无关；任何流程设计冲突时以此为准。

## P1 · 远端才是共享内存

几个工作区之间不共享磁盘、不共享上下文。能跨过去稳定传递的只有**已提交并推送**的内容：任务卡、交接单、state.json、代码提交。

- 没 push 的改动，在下一棒眼里等于不存在。
- 聊天窗口、本地草稿、未收起的终端、stash 都不是交接介质。
- 顾问席没有写权时，它的任务卡和评审意见同样要落成文件推上去。

## P2 · 接力单位是「一张卡 + 一个分支 + 一次绿色提交」

不是「聊完换人」，而是「做完一件能验收的事、推到远端再换人」。

- 一张卡只写一个目标，且必须能写成验收命令。
- 写不出验收命令的需求回炉重写，不许实现席自行发挥。
- 绿色提交是硬门槛：红着交出去，错误会被下一棒当成事实继续放大。

## P3 · 一条任务一条分支，主干只接受合并

- 远程分支存在即视为认领；别人看到同名分支应换卡，不硬抢。
- main 开保护：禁止直推、必须构建通过、至少一次评审。
- 冲突在自己分支上 rebase 解决，不在 main 上解决；禁止 force push 覆盖他人提交。

## P4 · 交接标准是「对方 fetch 一次就能继续」

交接单必须跟着 commit 推到远端，并写清分支名与最后一次提交号。

- 下一棒用提交号定位现场，不从 main 猜现状。
- 交接单 ≤ 400 字，每条踩坑 ≤ 2 行；详细材料放仓库内文件并用链接引用。
- 检验标准：下一棒拿到这张纸，一句都不问就能开工。

## P5 · 换模型也是交接，落盘才算数（V1.3）

「单工作区多会话」解决的是换会话时的接力（硬交接），靠会话结束这个天然断点触发落盘。同一会话内换模型没有断点，因此按**软交接**处理：

- 不换分支、不换任务卡，但必须打检查点：commit + push、刷新 state.session、写检查点交接单、重述关键约束。
- 新模型第一步只读仓库事实，不沿用上一模型的口头结论；仓库与聊天冲突时以仓库为准。
- 模型身份写入 `state.session.model_history`，否则事后无法审计哪一棒由哪个模型完成。

完整规则见 `single-workspace.md`。

## 单工作区适配（C1）

没有物理目录隔离时，用**分支 + state.json + 交接单**替代目录隔离：

1. 同一工作区里切换角色前，先把当前改动 commit + push，再写交接单和 state。
2. 换席位：若剩余工作可独立验收，原卡收口后从最新 main 开新分支；否则续同一条分支，只追加提交。
3. 每一次切换都留下可 fetch 的证据；「commit + push 才算交接」在单工作区同样适用，甚至更重要——因为本地文件和聊天记录都还在原地，最容易让人误以为已经交接。

## 两种交接对照

| 维度 | 硬交接（换会话 / 换席位） | 软交接（同会话换模型） |
| --- | --- | --- |
| 触发 | 会话结束、任务转手 | 会话中切换模型（含平台自动降级 / 升级） |
| 分支 / 卡 | 换棒或续棒，owner 换席位 | 不换分支、不换卡，task_id 与 status 保留 |
| 必做 | commit + push + 交接单 + state | commit + push + 检查点交接单 + state.session |
| 事实来源 | 仓库 | 仓库优先，聊天仅作背景 |
| 主要风险 | 没 push 等于没交接 | 聊天惯性、上下文截断、工具能力差异、身份不可审计 |
