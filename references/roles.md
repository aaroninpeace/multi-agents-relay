# 席位、能力矩阵与编队

> 产品名只是「当前示例」，Skill 会被不同桌面 Agent 加载。真正稳定的是**角色协议**：产品席 / 评审席 / 调度席 / 实现席 / 修红席 / 原型席 / 快修席。换一批工具时只需替换括号里的示例。

## 七个席位

| 角色 | 当前示例 | 擅长 | 边界 |
| --- | --- | --- | --- |
| 产品席 | 豆包工作（对话式办公） | 需求澄清、拆任务、写验收标准、读长文档 | 偏对话，跑构建和批量改码不如 IDE / CLI；适合出卡和读交接单 |
| 评审席 | 千问工作（对话式 / 长上下文） | 方案与接口评审、找逻辑漏洞、事后复盘 | 结论可信，但别让它守着终端跑测试；结论要落进仓库 |
| 调度席 | WorkBuddy（办公自动化） | 多步流程编排、进度汇总、生成周报 | 强在流程，弱在代码细节；只动自己负责的文档和脚本 |
| 实现席 | CodeBuddy（IDE Agent） | 整文件改写、重构、补单测 | 长任务容易发散，必须用任务卡限定改动目录 |
| 修红席 | ZCode（终端 / CLI Agent） | 跑测试、批量替换、把构建从红改绿 | 不擅长从零设计交互，别让它做产品判断 |
| 原型席 | Trae（IDE Agent） | 前端页面、交互原型、快速起版 | 风格和架构一致性要由接手方兜底 |
| 快修席 | MiniCode（轻量 CLI Agent） | 小改动、脚本、格式化、提交前清理 | 跨文件改造容易漏改，改完必须自己跑一遍构建 |

## 缺席席位

团队里总有一个「只出主意、不落文件」的成员。给它**顾问席**：产出任务卡和评审意见，**不碰代码**（READ ONLY → WRITE NEVER）。这样判断力照样能用，又不会制造冲突。没有终端或不能 push 的模型在换模型场景中也降为顾问席。

| 千问工作 | OK | ~ | ~ | ~ | ~ | OK | 评审席 |

开工前在每个客户端上实际开一次分支、跑一次 build 再定席位。跑不动构建的只能当顾问席。

## 三种编队

### 双人接力（最小可用）

- **实现席**：认领分支、按卡实现、跑完自检门并推送。
- **修红席 / 复核席**：fetch 分支跑测试，只读 diff，把红修绿。
- 顺序：任务卡 → 实现席推分支 → 复核席 fetch 复核 / 修红 → 人合并 main。
- 适用：个人项目、单功能迭代、先把流程跑通。
- 注意：两个克隆各写各的分支，靠远端串行；别互相覆盖工作区目录，也不要互相同步半成品。

### 三角编队（上线项目稳态配置）

- **产品席**：澄清需求，产出任务卡并推到 main。
- **实现席**：在 `agent/T-xxx` 分支实现并写交接单。
- **评审席**：读远端 diff 找漏洞，给通过或退回结论。
- 顺序：出卡并推送 → 实现并推分支 → 评审远端 diff → rebase 后合并。
- 适用：已上线站点、需要需求把关和代码复核的功能开发。
- 注意：评审席只读分支、不改分支；一旦动手推代码，就没有第二双眼睛了。

### 七人全链（席位齐全，最考验交接质量）

- **需求（产品席）**：一句话需求变成 1–3 张卡并推送。
- **评审席**：方案预审 + 合并前基于远端 diff 复核。
- **调度席**：维护 `.agent/log.md`、排优先级、汇总进度。
- **原型席**：在自己分支做出能点的版本，定交互。
- **实现席**：按卡落地并补单测。
- **修红席**：把构建、测试、lint 拉回全绿。
- **快修席**：格式化、小修、提交前清理。
- 顺序：需求 → 原型分支 → 实现分支 → 修红 → 清理 → 评审 → rebase 合并。
- 适用：重构、多页面改造、多人协作的中大型任务。
- 注意：七个克隆就是七份上下文，交接单和分支名是唯一索引；缺一条后面全乱。

换人可以，席位职责别乱：写代码的、只读评审的、只管流程的混在一起，验收就形同虚设。
