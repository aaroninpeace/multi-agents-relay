多 Agent 接力手册

让多个独立工作区的 Agent，在同一个 Git 仓库里接力完成项目

PLAYBOOK / V1.3 版本 V1.3 ｜ 更新 2026.11 ｜ 适用 同一台电脑上多客户端 / 多会话协作，含同会话换模型

核心原则：多个 Agent 各自开着独立的工作区、各自克隆了一份仓库，从来不在同一块磁盘上。所以接力的支点不是某个共享目录，而是同一个 Git 远端：谁开工，谁先把任务分支推上去；谁收工，谁把交接单和代码一起推回来。

交接棒 = 一张任务卡 + 一次绿色提交。谁都能改，但只有推上去的改动才算数。

独立工作区各 Agent 各自克隆，磁盘互不共享
共同远端唯一的公共内存：commit + push
接力循环七步固定动作，每棒产出下一棒的输入

01核心原则：先接受 Agent 之间没有共享记忆

它们不会互相读心，也不会共享上下文。多个克隆各管各的本地目录，能跨过去传递的只有已经推送的提交，所以流程要围绕分支和交接单来设计。

P1 · 远端才是共享内存

几个目录之间不共享任何东西，本地文件传不过去。能跨克隆稳定传递的只有已经提交并推到远端的内容；没 push 的改动，在下一棒眼里等于不存在。

P2 · 接力单位是「一张卡 + 一个分支 + 一次绿色提交」

不是「聊完换人」，而是「做完一件能验收的事、推到远端再换人」。一张卡一个目标，卡上写死验收命令，交接才有边界。

P3 · 一条任务一条分支，主干只接受合并

多个克隆同时开工时，写权靠分支隔离。远程分支就是认领凭证：分支已经在远端，说明有人在做；main 只能通过合并进入，不能直推。

P4 · 交接标准：对方 fetch 一次就能继续

交接单必须跟着 commit 推到远端。留在本地草稿、聊天窗口或某个没收起的终端里的说明，下一棒永远看不到。

P5 · 换模型也是交接：落盘才算数 V1.3 新增

「单工作区多会话」解决的是换会话时的接力（硬交接）。但同一会话里前后换模型，没有「会话结束」这个天然断点：未提交的改动会被新模型就地继承，聊天记录还留在窗口里，容易被当成事实来源。模型换了，上下文窗口、工具能力、指令遵循强度也可能跟着变。

所以换模型按软交接处理：不换分支、不换任务卡，但必须打检查点——commit + push、刷新 state.json（记录 session / model / checkpoint_commit）、写一份 ≤400 字的检查点交接单，并把关键约束（allowed_paths、验收命令、DoD、当前 status）重述一遍。新模型的第一步只读仓库事实，不沿用上一模型的口头结论。完整规则见 §11-6。

02工具分工：先分清谁能写代码，谁只该出主意

各席位都在自己的克隆里工作，分工说的是「谁适合干什么」，不是「谁能碰到文件」。真正的写权由一张卡一条分支决定。

03同步总线：几个克隆之间，唯一的通道是远端

本方案的前提：各客户端各自工作在自己的目录、各有一份克隆，唯一共同点是同一个 Git 远端。只要都能 fetch / push，就能接力；连远端都够不着的客户端，只能当顾问席——出任务卡和评审意见，代码由别人推。

三条基本认识

本地目录传不过去各份克隆各在各的盘上，你改的文件别人看不见；磁盘不是共享内存。
远端才是总线只有 commit + push 之后的内容，才存在于所有工作区都能读到的公共空间里。
分支就是锁远程分支存在即视为被认领，不需要锁文件服务，也不会出现两个人静默覆盖。

一棒到底要跑哪几条命令

01先对齐远端
git fetch --all --prune
git switch main && git pull --ff-only

开工前先看远端已有哪几张卡、谁在写；本地不 fetch 就等于在看昨天的世界。

02建分支并推送，才算认领
git switch -c agent/T-014
git push -u origin agent/T-014

推得上去说明没人占；提示 already exists 就换一张卡，不要硬抢。

03在自己的克隆里做完并自检
pnpm build && pnpm test
git status --short

改动只落在本卡允许的文件里；构建必须在你自己的工作区跑绿。

04交接单和代码一起推
git add .agent/handoffs/T-014.md src/
git commit -m "feat(x): … [T-014]"
git push

交接单留在本地等于没写；分支名和最后一次提交号必须写进交接单。

05rebase 后合并回主干
git fetch && git switch agent/T-014
git rebase origin/main
git switch main && git merge --no-ff agent/T-014

冲突在自己的分支上解决，不在 main 上解决；合并前再跑一次构建。

总线纪律

  • 本地目录不共享，远端才共享：任何要交接的东西，先 commit，再 push。
  • 认领用远程分支实现，不需要任何锁服务；分支推成功才算占到这张卡。
  • 顾问席（豆包工作、千问工作）可以只读，但它们的任务卡和评审结论同样要推上去，否则下一棒看不到。
  • 禁止 force push 覆盖别人的分支；push 被拒就先 fetch + rebase，再重试。
  • 一张卡一个分支；要并行就得拆卡、拆文件，不能两个克隆改同一段代码。

中途换人：换棒，不换分支

拆卡是用来缩小交付粒度的，不是用来转移责任的。判断只有一个标准：这一棒能不能交出一个可验收的增量。能，就拆；不能，就续棒——同一条分支往后追加提交，谁接手谁 push。

情形处置分支交接物
只是换执行者，边界不变续棒同一条 agent/T-014 继续追加提交，不新建分支、不复制卡WIP 交接单，写清最后一次提交号
剩余部分能独立验收拆卡原卡收口后合并进 main，再从最新 main 拉 agent/T-015原卡关闭说明 + 新卡（含新的验收命令）
方向错了或卡本身不成立废卡分支打 tag 留档后丢弃，不合并；从 main 重新开卡一句话写清为什么废，别让下一棒重走一遍

续棒的场景：剩下的活还不够独立验收——改到一半的组件、没跑完的测试、只有你知道的临时状态。

换棒三步

# 第一棒：半成品必须先推上去（不合并）
git add -A
git commit -m "wip(T-014): 做完 X，卡在 Y"
git push

# 第二棒：接同一条分支，先看最后一棒停在哪
git fetch --prune
git switch agent/T-014 && git pull --ff-only
git log --oneline -3

# 收口后照常回主干
git switch main && git pull --ff-only
git merge --no-ff agent/T-014

WIP 交接单五格

  1. 现状：一句话说清当前能不能构建、能不能跑。
  2. 已完成：列到提交号，别写「差不多了」。
  3. 卡在哪：贴失败命令的原始输出，不要转述。
  4. 下一动作：只写一个可执行动作，不写方向。
  5. 不要碰：明确禁止改的文件与原因。

换人时的五条禁令

  • 同一张卡不要在两个克隆各开一条分支，双写必然冲突。
  • 不要把未提交的改动贴进聊天窗口，换台机器就丢了。
  • 不要用 git stash 交接，它只存在你那台机器上。
  • 不要为了换人把红的分支合进 main，先修绿或先回退。
  • 不要把拆卡当默认动作，拆一次就多丢一次上下文。

04车间协议：几份克隆各写各的，靠什么不打架

不需要任何插件、服务器或锁服务。一个共同远端加几条分支约定，就把「谁在做、做到哪、下一步是什么」变成所有克隆都能 fetch 到的事实。

仓库结构

origin/                        # 各克隆共同指向的唯一远端
├─ main                        # 集成分支：只接受合并，开保护规则
├─ agent/T-014                 # 一卡一分支：分支存在 = 已被认领
└─ agent/T-014-review          # 可选：评审留痕分支（团队要求时）

任一份克隆内的结构（各份一致，靠 git 同步）
repo/
├─ AGENTS.md                   # 技术栈、三条验收命令、目录约定、禁止事项
├─ .agent/
│  ├─ tasks/T-014.md           # 任务卡：目标 + 验收命令 + 允许改动范围
│  ├─ handoffs/T-014.md        # 交接单：现状 + 已做 + 未做 + 下一动作
│  ├─ log.md                   # 只追加流水账：谁、何时、推到哪个分支
│  └─ state.json               # 当前阶段、认领分支、阻塞项
└─ src/                        # 业务代码：只在本卡分支上改

五条前提

  1. AGENTS.md 跟代码一起进仓库：它随 fetch 同步，不是谁本机的私人笔记。
  2. 任务卡写在 main 上（或专门的派单分支）并推送，其他人 fetch 之后才知道有这张卡。
  3. 任务卡只写一个可验收目标。写不出验收命令的需求，回炉重写。
  4. 改动只在 agent/T-xxx 分支上进行；main 开保护：禁止直推、必须构建通过、至少一次评审。
  5. 交接单必须写明分支名与最后一次提交号，下一棒用它定位，不靠猜。

05接力循环：每一棒的产出，都是下一棒的输入

把「换人」拆成固定动作，交接就不再靠记忆和自觉。任何一步没产出物，就不该进入下一步。

七步接力

01派单产品席（豆包工作）+ 人

卡片里不写「优化一下体验」，写「点击 X 出现 Y，build 通过」。范围、验收命令、不许碰的目录三项缺一不可；写完推上去，别放在自己克隆里。

OUT .agent/tasks/T-014.md（已推送）　RULE 一张卡一个可验收目标

02同步远端任一实现席

git fetch --all --prune，看一眼 origin 上已经有哪些 agent/T-xxx。已经有分支的卡别接，接了就是两个人的冲突。

OUT fetch 后的远端分支列表　RULE 先看有没有人认领

03建分支认领实现席

从最新 main 切出分支，第一次 push 成功即完成认领。推不上去说明卡已被占，回去换一张，不要改名硬挤。

OUT origin/agent/T-014　RULE 推成功才算占到

04只读勘察实现席

按顺序读 AGENTS.md、上一张交接单、相关源码和最近几次提交。输出现状 / 要改的文件 / 风险三点，确认后再动手。

OUT 接手的第一个 3 行结论　RULE 先读，后写

05单点实现 + 自检门实现席

改动超出任务卡的「允许改动」就停手拆卡。构建、测试、lint 必须在自己克隆里跑绿；修不动就如实写「仍红、卡在哪一行」。

OUT 本分支上的绿色提交　RULE 全绿才允许交接

06提交并推送交接单实现席

交接单和代码放在同一次 push 里，写清分支名、最后一次提交号、没做完的事和下一棒第一件事。踩过的坑写进去，那是这一棒最贵的产出。

OUT .agent/handoffs/T-014.md 已推送　RULE 别留在本地

07评审、rebase 与合并评审席（千问工作）+ 人

评审基于远端分支看 diff；通过后 rebase 到最新 main 再 --no-ff 合并。有问题退回第 5 步，并在卡上写明退回原因。

OUT review 结论 + 合并进 main　RULE 评审只读 diff，不直接改码

七个席位不必都上。最少两个人就能跑这套循环；人越多，越依赖第 6 步那张纸的质量。

06交接模板：把口头交接变成可复制的格式

模板的价值不在于写得多漂亮，而在于每一棒都填同样五个格子。空格一旦固定，缺什么一眼就能看出来。

07编队方案：关键在交接密度

编队不是越多人越好。席位越多，交接次数越多，每多一次交接就多一次信息损耗。先按任务复杂度选最小可行编队，跑顺了再加人。

双人接力

最小可用：两个克隆就能跑起来

CodeBuddy · 实现席认领分支、按卡实现、跑完自检门并推送

ZCode · 复核席fetch 分支跑测试，只读 diff，把红修绿

接力顺序 任务卡 → CodeBuddy 推分支 → ZCode fetch 复核 / 修红 → 人合并 main

适用 个人项目、单功能迭代、想把流程先跑通

两个克隆各写各的分支，靠远端串行；别去互相覆盖工作区目录，也不要互相同步半成品。

三角编队

上线项目的稳态配置

豆包工作 · 产品席澄清需求，产出任务卡并推到 main

CodeBuddy · 实现席在 agent/T-xxx 分支上实现并写交接单

千问工作 · 评审席读远端 diff 找漏洞，给通过或退回结论

接力顺序 出卡并推送 → 实现并推分支 → 评审远端 diff → rebase 后合并

适用 已上线站点、需要需求把关和代码复核的功能开发

评审席只读分支、不改分支；它一旦动手推代码，就没有第二双眼睛了。

七人全链

席位齐全，但最考验交接质量

豆包工作 · 需求把一句话需求变成 1-3 张卡并推送

千问工作 · 评审方案预审 + 合并前基于远端 diff 复核

WorkBuddy · 调度维护 .agent/log.md、排优先级、汇总进度

Trae · 原型在自己的分支上做出能点的版本，定交互

CodeBuddy · 实现按卡落地并补单测

ZCode · 修红把构建、测试、lint 拉回全绿

MiniCode · 快修格式化、小修、提交前清理

接力顺序 需求 → 原型分支 → 实现分支 → 修红 → 清理 → 评审 → rebase 合并

适用 重构、多页面改造、多人协作的中大型任务

七个克隆就是七份上下文，交接单和分支名是唯一索引；缺一条，后面全乱。
换人可以，席位职责别乱：写代码的、只读评审的、只管流程的，一旦混在一起，验收就形同虚设。

08冲突与验收：让接力不变成互相拆台

多 Agent 协作的失败，几乎都不是「模型不够聪明」，而是边界没定。写权、验收标准、回滚路径三件事必须提前写死，否则每一棒都在替上一棒擦屁股。

G1 · 写权与分支控制

几个克隆互不相识，写权靠分支隔离，不靠自觉。

  • 一卡一分支 agent/T-xxx：分支推到远端即视为认领，别人看到就换卡
  • 禁止直推 main，开保护规则：至少一次评审、必须构建通过
  • push 被拒先 fetch + rebase，不许 force push 覆盖他人提交
  • 同一个文件同一时间只归一个分支，跨席位改动先拆卡

G2 · 验收门（DoD）

解决「算不算做完」的问题，标准写死，不许各说各话。

  • build / test / lint 三条命令全绿，且是在本分支本次改动后跑的
  • 改动范围与任务卡一致，超范围的部分拆成新卡
  • 分支、交接单、提交信息都已推到远端，别人 fetch 得到
  • 无密钥、无调试代码、无注释掉的旧实现残留

G3 · 失败与回滚

解决「接不下去」的问题，先止损，再定位。

  • 接手方复现失败：checkout 交接单里写的提交号，别从 main 猜现状
  • 分支落后太多：先 rebase origin/main，再跑验收命令
  • 两个分支改了同一文件：合并在先，人工裁决冲突，不许强推覆盖
  • 任务卡本身有歧义：退回产品席改写，实现席不许自行发挥

六条全过，才算这张卡结束

#DoD 检查项通过
1构建通过（本分支本次改动后跑的）☐
2测试通过☐
3lint 无新增问题☐
4改动范围 = 任务卡范围☐
5分支与交接单已推送☐
6无密钥 / 调试残留☐
三条命令必须是「本次改动之后」跑的。改码前的绿色构建不算数。

Fail Fast · 接不下去时怎么办

  1. 先停写，别在红的基线上继续叠改动
  2. 回退到上一个绿色提交，保留现场
  3. 把失败复现步骤写进交接单
  4. 拆小任务卡，重新派单给另一个席位
回滚不是失败，带着错误往前走才是。

信号 → 处置对照

风险可观测信号处置动作
看的是过期代码本地很久没 fetch，分支落后 main 一大截开工和交接前都 git fetch --all --prune，以远端分支为准
两个克隆抢同一张卡push 提示远程分支已存在让出这张卡，或拆卡另开分支；不要改名硬挤
直接改 main，回滚很难main 出现没有评审的提交立即 revert，补齐 main 保护规则
交接单留在本地下一棒 fetch 不到 handoff 文件把交接单和代码放进同一次 push，再宣布交接
构建一直红，没人敢接连续两棒都没让分支变绿降级为最小修复卡，只修构建，别的都不做

09反模式：六种让接力断掉的写法

下面每一条都真实发生过，而且都不会报错——它们只是让效率悄悄归零。出现任意一条，先停写。

#反模式为什么致命
01把本地目录当共享盘几个克隆互不相通，改完不推等于没改；谁也看不到你硬盘上的文件
02直接 push 到 main几个克隆抢一个入口，未审代码和冲突会一起进主干，回滚成本翻倍
03交接单只在本地草稿里下一棒 fetch 不到，只能从提交历史里考古，沟通成本全落到人身上
04把聊天记录复制粘贴当交接噪声大、关键结论埋在中途，下一棒还得重读一遍，等于没交接
05一张卡塞一整个功能「把支付做完」无法验收，实现席必然发散，最后谁也不敢合并
06跳过验收门直接换人这一棒的错误会被下一棒当成事实继续放大，越往后越难回滚

统一止损动作

不管撞上哪一条，处置顺序都一样：停写 → 回滚到上一次绿色提交 → 补齐任务卡 → 重新派单。

不要在红着的代码上继续叠改动，也不要靠「我记得当时是这么想的」来补救。

10落地清单：今天就能做完的八件事

不需要装插件、不需要写服务。先建远端、开保护、拿一个真实小需求跑一遍，流程就能立起来。

#动作为什么完成
01建一个共同远端（裸仓库 / GitHub 私库），各客户端全部 clone远端是各份克隆之间唯一的总线☐
02给 main 开保护：禁止直推、必须构建通过、至少一次评审没有保护分支，前面的约定都是口头禅☐
03写 AGENTS.md 并提交：技术栈、三条验收命令、目录约定、禁止事项它随 fetch 同步，所有席位开工第一条就是读它☐
04约定分支命名 agent/T-xxx，一张卡一个分支远程分支就是认领凭证☐
05给每个客户端固定一段「席位 Prompt」，写清 fetch / push 责任放在各自自定义指令里，避免每次重贴☐
06确认每个实现席都能在自己克隆里跑 build跑不动构建的只能当顾问席☐
07用一张真实小卡跑通全流程：推分支 → 交接 → rebase → 合并越小越好，重点是跑通，不是做完☐
08一周后复盘：数返工次数与「接手方提问次数」提问次数下降，说明交接单真的在起作用☐

全部勾完之后，最有价值的动作是复盘：统计一周内「接手方提问次数」和返工次数。这两个数字降下来，说明协议真的生效了。

最后一句话

不要追求让 Agent 互相聊天，先让每一棒的产出都能被下一棒原样接住。
接力跑得快不快取决于最后一棒，而最后一棒能跑多快，取决于第一棒留下的那张纸。
先让每一棒可被接住与其指望这些客户端互通上下文，不如把结论推到同一个远端。提交历史是它们唯一的公共内存。
一次只推进一个可验收目标卡片越小，交接越轻。任务卡写不出验收命令，说明需求还没想清楚。
构建没绿就别换人红着交出去，错误会被下一棒当成事实继续放大，回滚成本翻倍。

能力矩阵里的强弱是「按工具形态」给的经验判断，不是任何厂商的官方规格；请以你本机实际版本为准，逐个开一次目录、跑一次构建再定席位。

11把手册升级为可执行的 Skill（V1.2 评审增补 · V1.3 补充）

前 10 章把「人怎么接力」讲透了。但要让桌面 Agent 加载即用，还差一层「机器可执行契约」。本章是 V1.2 的评审增补：先给总体判断，再给 14 条具体意见（分三组），最后给一份可直接落地的改造蓝图。V1.3 追加 §11-6：把「同一会话内换模型」纳入交接协议，补齐 C1 的覆盖边界。

总体判断

9 / 10

一句话结论：这份文档的「协议设计」已经成熟，问题不在讲得对不对，而在讲给人听，没讲给 Agent 执行。改造重心是补触发、补脚本、补 schema，而不是重写这 10 章。

A 组 · 定位与触发（4 条，决定 Skill 会不会被用对）

A1手册 ≠ Skill：缺可执行的入口指令

现状全文是「协议说明」，讲清了为什么这样做、怎么分工、流程是什么。

问题Skill 是给 Agent 加载的执行指令，需要「用户说什么 → 执行什么 → 产出什么」。当前没有一句告诉 Agent 何时触发、触发后第一步做什么。

建议新增 SKILL.md，frontmatter 写清触发场景；正文首段给「加载后立即执行的 3 步」：读 state.json → 判定当前状态 → 输出下一动作。原 10 章降级为 references/。

A2缺触发条件与反向排除

现状没有定义「用户说什么话时启用本流程」。

问题Agent 不知道何时加载，可能在用户只想问一个小问题时套上七步接力，反而添乱。

建议定义触发词：多 agent 协作 / 接力 / 交接任务 / 派单 / 接手 / 跨会话继续项目；并写明反向排除：单 Agent 一次性小任务不触发。

A3产品名硬编码，换一批工具就要改全文

现状豆包工作 / 千问工作 / WorkBuddy / CodeBuddy / ZCode / Trae / MiniCode 贯穿能力矩阵、席位、编队三处。

问题Skill 会被不同桌面 Agent 加载，这些名字对加载者无意义；工具一换全文失效。

建议抽象为「角色协议」——产品席 / 评审席 / 调度席 / 实现席 / 修红席 / 原型席 / 快修席（文档已有角色名），产品名降为括号内「当前示例」，角色定义单独放 references/roles.md。

A4单文件过大，无法高效加载与检索

现状正文嵌在压缩脚本里，整份文档体积很大。

问题Skill 加载的是文本，打包后的脚本无法被 Agent 有效读取，grep 定位也困难。

建议按渐进式披露拆成 SKILL.md（<5k 字）+ references/ + scripts/ + assets/。本 HTML 保留为「人类阅读版」，两者并存不冲突。

B 组 · 可执行性（5 条，决定接力可不可靠）

B1命令散落在代码块里，应固化为脚本

现状5 条命令、换棒三步、同步命令都散在代码块，靠 Agent 手抄。

问题git rebase / merge 顺序抄错代价高；不同工作区路径不同，照抄易失败。

建议固化为 relay-init/claim/sync/verify/handoff/merge.sh 六个脚本，统一接收 TASK_ID 参数，Agent 直接调用。

B2state.json 只提名，无 schema / 状态机

现状仓库结构里写「当前阶段、认领分支、阻塞项」，但全文没有字段定义、状态枚举、转移规则。

问题不同 Agent 写出不同结构，下一棒无法可靠解析，状态机会退化成自由文本。

建议给固定 schema（见下方蓝图）与状态枚举：todo → claimed → in_progress → handoff → in_review → merged，旁路 blocked / abandoned。

B3DoD 六条未脚本化，容易「自报已完成」

现状六条 DoD 是给人看的 checkbox。

问题Agent 可能声称完成但实际没跑 build、没 push 交接单、改动越界。

建议relay-verify.sh 自动校验：diff 范围是否在 allowed_paths、分支是否已 push、交接单 last_commit 是否等于 HEAD、验收命令退出码是否为 0。全过才允许写 status=handoff。

B4任务卡 / 交接单缺 frontmatter，解析脆弱

现状模板是纯 Markdown 标题段落（「## 分支」「最后提交：a1b2c3d」）。

问题Agent 靠正则抠「分支：xxx」，格式稍变就解析失败。

建议加 YAML frontmatter：任务卡 id/title/branch/allowed_paths/acceptance；交接单 task_id/branch/last_commit/status/done/remaining/next_action/pitfalls。

B5验收指标无采集字段，复盘取不到数

现状落地清单第 8 条要统计「接手方提问次数 / 返工次数」，但没定义埋点。

问题到了复盘节点无从取数，「提问次数下降」无法验证。

建议log.md 固定字段（时间戳 / 角色 / task_id / 事件类型），事件枚举 claim / handoff / verify_fail / merge / rework / question，用脚本聚合。

C 组 · 健壮性与边界（5 条，决定复杂场景扛不扛得住）

C1未覆盖「单工作区多会话」接力 V1.3 已细化

现状全篇假设多台机器、多份克隆。

问题Skill 常见用法是同一 Agent 在同一工作区跨会话接力，没有物理目录隔离；更进一步的「同一会话内换模型」连会话断点都没有（见 §11-6）。

建议补一节「单工作区模拟接力」：用分支 + state.json + 交接单替代目录隔离，切角色时 commit/push 再切分支；强调「commit+push 才算交接」同样适用。覆盖边界：该方案不能直接覆盖「同一 Agent、同一会话、前后不同模型」——那是软交接，规则见 §11-6 与 P5。

C2缺人工介入阈值，Agent 可能互相退单死循环

现状护栏 G3 说「退回产品席改写」，但产品席也可能是 Agent。

问题两个 Agent 可能退来退去，无人叫停。

建议定义 human-in-the-loop 触发：verify_fail ≥ 3 次 / 验收命令写不出 / 涉及生产凭据或数据迁移 / 同文件冲突无法裁决。触发即写 status=blocked 并明确 @人。

C3凭据与权限是盲区

现状「不要碰 .env*」写得很好，但没说 Agent 用什么身份 push。

问题共享 deploy key / token 有泄露与越权风险。

建议每席位独立凭据、最小权限（仅目标仓库）、token 不落盘只走环境变量、push 审计写 log.md。

C4缺上下文契约：交接单会吃掉下一棒的窗口

现状交接单「五格」但没有长度约束。

问题长交接单反而降低接力质量——读不完或挤占推理空间。

建议单张交接单 ≤ 400 字、每条踩坑 ≤ 2 行，详细材料放 assets/ 用链接引用。

C5协议版本与回滚机制未定义

现状文档自身标 V1.1，但没说协议版本如何演进。

建议交接单 frontmatter 带 schema_version；模板变更做兼容读取；Skill 用语义化版本，破坏性变更升主版本。

补充 · 同会话换模型：软交接检查点 V1.3 新增

覆盖判定：C1 的「单工作区多会话」不能直接覆盖「同一 Agent、同一会话、前后使用不同模型」。多会话接力靠「会话结束」这个天然断点触发 commit + push + 交接单；同一会话内换模型没有断点，未提交的改动会被新模型就地继承，而聊天记录还留在窗口里，会跟仓库抢「唯一事实来源」的位置。结论是：机制可复用，但必须补一条软交接规则，否则换模型后的第一步行为没有约定，接力质量靠运气。

① 两种交接的边界

维度硬交接（换会话 / 换席位）软交接（同会话换模型）
触发时机会话结束、任务转手、有人退出用户在同一会话中切换模型（含被平台自动降级 / 升级）
分支 / 任务卡换棒换分支（或同分支交接），owner 换席位不换分支、不换任务卡，task_id 与 status 原样保留
必做动作commit + push + 交接单 + state.json，下一棒 fetch 后从零读仓库commit + push + 检查点交接单 + state.json 记录 session/model；新模型先读仓库再续做
事实来源仓库（state.json / 交接单 / commit）仓库优先，聊天记录仅作背景；两者冲突以仓库为准
特有风险没 push 等于没交接聊天惯性沿用旧结论、窗口变小导致早期约束被静默截断、工具能力差异、模型身份不可审计

② 换模型前：落盘四件事（Pre-switch Checkpoint）

01把进度写成提交并推送

当前改动全部 commit + push。聊天里说「改好了」不算；没 push 的改动在新模型眼里不存在。

02刷新 state.json 的 session 段

写入 session.id、handoff_kind="model_switch"、checkpoint_commit、updated_at，并向 model_history 追加旧模型及其截止提交。owner 仍写席位不写模型；status 不变。

03写一张检查点交接单

沿用 §6-2 五格结构，额外补一段「约束重述」：allowed_paths、验收命令、DoD、当前 status 各一行。全文 ≤ 400 字，每条踩坑 ≤ 2 行；详细材料用链接指向仓库内文件，不塞进聊天。

04在会话里打出分界线

输出固定标记 ⟪RELAY-CHECKPOINT: T-014 @ <commit> @ <旧模型> → <新模型>⟫。它只是给人看的定位锚，权威仍在仓库；新模型不得把标记本身当作状态来源。

③ 换模型后：先绑定，再动手（Post-switch Re-bind）

  1. 新模型第一个动作是读 state.json → 读检查点交接单 → 读 git log -1，然后逐条复述「约束重述」四行。
  2. 绝不直接沿用聊天里上一模型的口头结论。仓库与聊天冲突时以仓库为准，并在 log.md 记一条 model_rebind_mismatch。
  3. 窗口变小：先把长聊天压成交接单，必要时开新会话转硬交接。不要让早期约束在新窗口里被静默截断。
  4. 工具能力不同：新模型没有终端或不能 push 时，降级为顾问席（只出卡 / 评审），写权交回有终端的会话，按硬交接走。
  5. 复述无误后，把 session.model 改为新模型标识，再继续任务；若发现状态不一致，先写 status=blocked 并按 C2 @人。

④ 三个高频坑与止损

坑表现止损动作
聊天惯性新模型把上一模型「我们决定这样改」当成已落盘事实，跳过 state.json强制「先读仓库再动手」；复述约束四行后才能改文件
上下文截断小窗口模型继承长会话，allowed_paths / 验收命令在中部被丢掉换模型前压交接单 + 重述约束；必要时转硬交接开新会话
身份不可审计只记席位不记模型，事后分不清哪一棒是哪个模型做的session.model_history 逐次记录，log.md 事件带 model 字段

⑤ 脚本层影响

在 §11-5 的六个脚本之外，增加一个 relay-checkpoint.sh：入参 TASK_ID 与 NEW_MODEL，负责「commit + push → 写 state.session → 生成检查点交接单骨架 → 打印分界线标记」。relay-verify.sh 增一条校验：handoff_kind=model_switch 时，检查点交接单的 checkpoint_commit 必须等于 state.json 同一字段且已存在于远端。原六个脚本语义不变。
